## 0. 一句话目标

采集箱里积压的 76 条非 1688 来源商品（拼多多 42 / Temu 30 / 亚马逊 4），
按平台分三期，每期把该平台从 ① 采集提炼跑到 ⑭ 保存落库，
每期先 dry-run 到 ④ 属性审核交人核对，确认后才继续往后跑。

### 1.3 各平台的数据差异（已摸清，分期设计的依据）

`SourceProduct` 契约有 11 个字段（见 `sources/base.py` 的 dataclass docstring）。
各平台实际能产出的部分不同，**下游阶段对缺失字段的反应就是各期的主要风险点**：

| 字段 | 1688 | 拼多多 | Temu | 亚马逊 | 缺失时下游怎么办 |
|---|---|---|---|---|---|
| `title` | 中文 | 中文 | 中文译文 | **英文** | 阶段⑤ 标题重写的提示词假设源标题是中文 |
| `attributes` | 键表匹配切分 | `goodsProperty` 干净键值对 | 规格键值对 | 三种版式合并 + bullets + descText | 阶段④ 属性审核靠 LLM 对齐，键名不归一是刻意的 |
| `skuMap` | 颜色>尺码 | 卖家自定义两维 | 常单维（如「风格」） | 变体表 | 单规格商品由各适配器 `_spec_to_pair` 补两维 |
| `descText` | 有（2026-09-01 加） | **没有** | **没有** | 有（进 `attributes["商品描述"]`） | 阶段①b 抽明文尺码表整条链路失效 → ⑨ 全靠识图估算 |
| `unitWeightKg` | `unitWeight` | 克转千克，实测恒 0 故给 None | **恒 None** | `#prodDetails` 能拿到，单位不认给 None | 阶段⑩ 转 LLM 预估 |
| `videoUrl` | 空串（不取） | `videoGallery` 多为空 | `videoList` | `data-video-url` | 阶段⑬b 无视频直接 skipped |
| 尺码表原始结构 | 无（靠识图/文本） | 无 | **独有 `store.sizeGuide`**（`{show:0}` 表示无表） | 无 | Temu 这份结构目前只塞进 `extra` 留档，下游不读 |
| 图床域名 | `cbu01.alicdn.com` | 七牛，剥 `imageMogr2` | `img.kwcdn.com` | 亚马逊 CDN | 见下面 1.4 的硬编码问题 |
| 币种 | 人民币 | 拼团价人民币 | **按站点变**（日元站给 426 円） | 站点货币 | 阶段⑤ 价格宣称硬闸的注释假设人民币 |

### 1.4 会静默影响新平台的 1688 硬编码（施工时必须处理）

这些不是注释，是**判据代码**，新平台上会静默判错：

1. **`pipeline.py:6464` 描述图外链判据写死 alicdn**
   ```js
   const foreign = descImgs.filter(h => /alicdn\.com$/.test(h));
   ```
   这个 `descForeignCount` 被 `service.py:533` 用来判「⑬ 描述阶段要不要重跑」：
   图全是外链说明删图/英化成果丢了。新平台的描述图外链是 `img.kwcdn.com`（Temu）
   或七牛（拼多多），**永远匹配不上 alicdn**，于是 `descForeignCount` 恒为 0、
   `⑬ desc` 永远不进重跑集 —— 表现是 save 失败后续跑时描述区带着未转存的外链图，
   一路撞平台校验。
   正解是复用同一模块 `pipeline.py:6973` 的既有判据 `DXM_IMAGE_HOST_MARK`
   （`"dianxiaomi.com"`，正向匹配「已入图床」而非反向枚举各家图床），
   把 `foreign` 改成 `!h.includes('dianxiaomi.com')`。那处注释已经论证过
   为什么正向匹配主域更稳，这里跟随即可。

2. **提示词里写死「源商品参数（1688）」两处**
   `pipeline.py:1925`（标题生成）与 `pipeline.py:4613`（`_ATTR_PROMPT` 属性审核）。
   `_ATTR_PROMPT` 开头还写着「下面是 1688 源商品信息」。
   新平台上告诉模型「这是 1688 参数」而实际是亚马逊英文 bullets，属性对齐质量会掉。
   `product-info.json` 的 `source.platformName` 已经有中文平台名（`extract.py:750`），
   提示词改成占位符填进去即可，不必新增取数。

3. **阶段⑤ 价格宣称硬闸的注释假设人民币源价**（`pipeline.py:1832`）
   代码本身是「价格一律不许进标题」的硬闸，与币种无关，**不用改**。
   但注释里「LLM 只看到 1688 人民币源价」在 Temu 日元源上不成立，
   施工时顺手把注释改成平台无关的说法，免得后来者据此推错。

## 2. 分期方案

**切法：按平台切，一期一平台。** 每期自成闭环，跑完即可上量。
排序依据是难度递增：

| 期 | 平台 | 积压量 | 为什么排这个位置 |
|---|---|---|---|
| 一期 | 拼多多 | 42 条 | 最简单：导航可行、`goodsProperty` 是干净键值对、中文源标题与 1688 同构 |
| 二期 | Temu | 30 条 | 多一条硬前提：页签必须提前开着（见 3.2）；币种按站点变；独有 sizeGuide |
| 三期 | 亚马逊 | 4 条 | 最杂：英文源标题、无内嵌 JSON、属性三种版式、重量单位多样 |

**每期的执行闸门（三期一致）**：

```
第 1 步  ① 采集提炼 → 落盘 product-info.json（纯本地，零副作用）
         ⇒ 停下，把落盘数据交人核对：标题/属性/skuMap/图片数/重量/尺码表
第 2 步  人确认后 → ② 认领（真实建草稿，不可逆）→ ③ 类目 → ④ 属性审核
         ⇒ 再停一次，核对类目选得对不对、属性填得对不对
第 3 步  人确认后 → ⑤→⑭ 跑到保存落库
```

这个闸门设计对标本项目既有的活动管线与订单管线（默认 dry-run、变更动作留桩）。
**闸门只在每期首个商品上设**：同平台第二条起，数据形状已验证过，可以直接全跑。

## 3. 各期施工内容

### 3.1 一期：拼多多

**先做的通用修复**（三期共用，放在一期做掉）：
- 修 `pipeline.py:6464` 的 alicdn 硬编码（见 1.4 第 1 条）
- 两处提示词的「（1688）」改成按 `source.platformName` 填（见 1.4 第 2 条）
- 顺手改 `pipeline.py:1832` 的注释（见 1.4 第 3 条）

**首个商品的验证清单**：
1. `① extract` 落盘后核对：`skuMap` 两维形状对不对（拼多多规格是卖家自定义，
   实测样本是「款式/尺寸」不是「颜色/尺码」，靠位置取第一维当颜色）；
   主图/详情图的 `imageMogr2` 参数剥干净了没有、尺寸够不够 1340×1785 服装红线
2. `descText` 为空 → 阶段①b 会 skipped，`sizeMeasurements` 落空表 →
   确认阶段⑨ 走识图估算这条路能出结果
3. `unitWeightKg` 为 None → 确认阶段⑩ 的 LLM 预估被触发
4. `② claim` 起：拼多多源链接能不能被店小秘的「链接采集」认（`claim.py::crawl_link`）
   —— **这是一期最大的未知**，店小秘只保证支持 1688，采集页对拼多多链接的反应未探测。
   若店小秘不认，则这 42 条只能走「采集箱已有草稿 + rowid 模式」，
   即填「源链接|rowid」跳过 ②，这条路是通的（`service.py:2645` 的任务形态二）。

**产出**：`product-pdd-<goodsId>/` 工作目录 + 一条保存成功的草稿。

### 3.2 二期：Temu

**Temu 独有的硬前提 —— 页签必须提前开着**
`sources/temu.py:172` 记着：Temu 会把对商品页的**重新导航** 302 到
`login.html?login_scene=2`，同浏览器、同 URL、旁边页签正开着完整数据也照样跳。
故适配器优先 `adopt_open_page(f"-g-{gid}")` 复用已开页签，找不到才 navigate（大概率撞墙）。

**实际操作含义**：跑 Temu 源之前，人要先在调试 Chrome 里从站内点开商品页并保持开着。
撞墙时走 `wait_human` 提示人工、原地轮询等 600 秒（`sources/base.py:275`），不直接失败。
批量跑 30 条时这个前提很难满足 —— **二期要先确认清楚**：
- 是不是每条都必须人工预开页签（那 30 条的批量价值就没了）
- 还是登录态足够新时 navigate 也能过（则前提可放宽）

这个问题的答案决定二期是「批量管线」还是「半人工逐条」，**必须在二期开工第一步探明**。

**其余验证清单**：
1. 币种：Temu 按站点给不同币种（`_ZERO_DECIMAL` 表 + `_guess_currency`）。
   确认落盘的价格数值与币种标注对得上，别把日元当美元读（差 100 多倍）
2. `skuMap` 常是单维（实测样本「风格」）→ 确认 `_spec_to_pair` 补两维后
   `pivot_skus` 不会整条丢掉（这是 2026-08-28 offer 1014675972015 那个 bug 的同类）
3. `unitWeightKg` 恒 None → 同一期第 3 条
4. `store.sizeGuide` 目前只进 `extra` 留档、下游不读。二期评估：
   要不要把它接进 `sizeMeasurements`（Temu 源的尺码表是结构化的，比识图准）。
   **这是可选增强，不阻塞二期主线**，评估后单独决定

**产出**：`product-temu-<goodsId>/` + 一条草稿 + 「页签前提能不能放宽」的结论。

### 3.3 三期：亚马逊

**英文源标题是三期的主要改造点**
阶段⑤ 标题生成的提示词假设源标题是中文，要求「中文标题重写、去掉品牌名、
不得照抄源标题」（`pipeline.py:1918`），并且靠 `_brand_words` 从「源标题开头的
英文 token」认品牌 —— 而亚马逊标题**整条都是英文**，开头几个 token 往往正是品牌名
（亚马逊标题惯例是「Brand + 品类 + 参数」）。这一处在英文源上的行为要实测确认：
- `_brand_words` 会不会把整个标题都当品牌词过滤掉（那阶段⑤ 必然失败）
- 中文标题从英文源生成的质量如何

**其余验证清单**：
1. 属性三种版式合并（`#prodDetails` / `#detailBullets` / 服装类表）实测只有
   `#prodDetails` 有货 37 项，但服装类是反过来的。四条积压里若有服装类要单独看
2. `attributes` 里塞了 `商品要点`（bullets 前 8 条）与 `商品描述`（descText 截 800 字）
   → 确认阶段④ 属性审核的提示词吃得下这种长文本，别把 token 撑爆
3. 重量单位：`sources/amazon.py:175` 认「公斤/grams/pounds/ounces/g」，
   认不出给 None（宁可让 ⑩ 估也不填错值，差 350 倍）。确认实际样本的单位在表内
4. 变体表跨 ASIN（`dimensionValuesDisplayData` 给 `{ASIN: [风格名]}`）
   → 确认 `skuMap` 产出合理

**产出**：`product-amazon-<ASIN>/` + 一条草稿 + 英文源标题链路的结论。

## 4. 环境前提（三期共用）

**调试 Chrome 必须在跑**（登录态就靠它保存，不存 cookie 文件）：
```powershell
& "C:\Program Files\Google\Chrome\Application\chrome.exe" `
  --remote-debugging-port=9222 `
  --user-data-dir="C:\chrome-debug-manus"
```
2026-09-01 核查：9222 端口正跑着这个 profile，cookie 库
`C:\chrome-debug-manus\Default\Network\Cookies` 229 KB。
**在这个窗口里手动登录一次，登录态永久留在该目录**，下次同目录启动免登录，
`connect_over_cdp` 直接复用（`browser.py` 全程只接管、不新建 context）。

**不要改成 storage_state / 自存 cookie**。理由在 `browser.py:345`：
这几家的反爬不只看 cookie —— 同一个 URL 用 `page.goto` 会被 302 到登录页
（哪怕 cookie 完整），重放 cookie 起裸浏览器还会掉 `navigator.webdriver` 指纹。
项目一贯取向是「用户开着，我们只读」，不模拟登录、不重放。

各平台首次跑要在这个窗口里登录一次：拼多多、Temu、亚马逊。
店小秘的登录态本来就在（1688 管线一直在用）。

## 5. 不做的事

- **不新增 fallback 分支**（项目约定）。店小秘不认拼多多链接时，走既有的
  rowid 模式，不另造一条采集实现
- **不把属性键跨平台归一**。`SourceProduct` 契约明确写了这是刻意的：
  阶段④ 是把整个 attributes 塞进提示词交模型对齐，强行归一反而丢信息
- **不改 `pivot_skus` 的 `颜色>尺码` 形状**。阶段⑧⑨⑩⑪ 全按这个形状写死，
  换形状要动四个阶段
- **不动 1688 的工作目录命名**（不带平台前缀）。加前缀会让 34 个历史目录
  与状态文件全部失配，续跑从头再来
- **不做「验证性重跑」**。`claim.py` 头部记着：认领会真实创建草稿且不可逆，
  只能到列表里手动删。故每期首个商品的 ② 认领只跑一次
