## 四、绕不开的既有坑

搬运时会撞上的，按已实测结论办，别重新试：

1. **虚拟列表滚动每屏须等 180ms**。原 skill 的 120ms 在 Playwright 直连下不够（WebBridge 的 HTTP 往返开销间接补足了等待），表现为静默只读首屏 10 条。见记忆 `dianxiaomi-virtual-list-scroll-timing`。基准：上装成分 67 项。

2. **动态属性行的必填标记在内层 `span.attr-label.required`**，`label` 的 `title` 是空的。见记忆 `dianxiaomi-attr-required-in-inner-span`。基准：33 行中 18 必填。

3. **LLM `max_tokens` 需 16000**。推理模型先产 reasoning 再产 content，额度不足时 content 返回空字符串（表现为「调用成功但结果为空」）。见记忆 `publish-llm-max-tokens-16000`。

4. **JS 常量必须用 `r"""`**。普通字符串里 `\s` 被格式化工具「修正」后，Python 转义使 JS 收到字面 `s`，正则 `[*\s]` 变成「匹配星号或字母 s」。

5. **点击方式因场景而异，不要统一**：
   - 编辑页按钮（保存等）：JS `el.click()` 有效，`mouse_click` 与 CDP `dispatchMouseEvent` 被吞
   - 认领弹窗店铺复选框：必须真实点击，JS `.click()` 不触发 Vue
   - 素材图/SKC 悬停菜单：必须 CDP 真实鼠标移动
   Playwright 下每条都要重验。

6. **幽灵浮层**：同选项列表的多个字段共享浮层池，点在隐藏浮层上事件照样生效会改错字段。一切选项查找限定在「目标行附近唯一可见浮层」内（`top > -1000 && width > 50`，按距离取最近），每步前后清幽灵。

7. **`curl.exe` 子进程不能换成 httpx/requests**：Packy 的 Cloudflare 按 TLS 指纹拦截，403 error 1010。店小秘 COS PUT 同理。

8. **隐藏页签 rAF 节流**：窗口被遮挡时浮层定位算不出来（`getBoundingClientRect` 恒 -9999）。修复是 `Emulation.setFocusEmulationEnabled` + `Page.setWebLifecycleState`，每次导航后失效需重发（已收进 `browser.navigate`）。

### 三条踩坑（都已写进代码注释与记忆）

1. **「发布」下拉是 hover 触发，不是 click**。`btn.click()` 后页面上一个含「立即发布」
   的节点都没有；合成 `mouseover`/`mouseenter`/`mousemove` 才渲染出 `.ant-dropdown`。

2. **菜单有入场动画，`offsetHeight` 不能当判据**。逐帧采样（hover 后 0/900/2400ms）：
   t+900ms 时 inline style 是 `opacity:0` + `transform: matrix(0,0,0,0,0,0)`，
   容器与项的 `getBoundingClientRect()` 都是 0×0，而 `offsetHeight` **已经是最终值**
   72/32。用 offsetHeight 收敛会在动画中途退出、拿到 0×0 坐标。
   判据必须用**目标菜单项的 `rect.height > 0`**。

3. **发布成功只能去列表取证**。成功 toast 抓不到（自定义实现、转瞬即逝，轮询 12s
   一条没有），页面**也不跳转**（发布后留在编辑页），两个前端信号都恒为「没有」。
   判据改为：该 rowid 从草稿箱消失 或 出现在在线产品列表（`_publish_landed`）。
   行选择器必须写 `tr[rowid="<id>"]`——rowid 数字开头，不加引号是非法选择器。

### 同轮修掉的两个既有 bug

- **⑧ 尺码勾选**：源「均码」× 成人女装英文尺码（`one-size`/`XXS`/…）匹配不上，
  `fix_sizes` 把页面原本勾着的取消完还返回 ok，⑨ 才报「请先选择尺码」。
  修法：`_SIZE_ALIASES` 别名表（均码↔one-size，**不收** Asian/Petite/Tall 版型变体）
  + **先校验再动手**（源尺码全不匹配时立刻报错，不改动任何勾选）。
- **⑦ SKC 行按钮瞄点**：残留图片菜单盖住按钮中心，且它 Escape/合成 click 都收不掉
  （`parked` 恒 0），而原实现只在 `parked>0` 时重读坐标，于是一次都没重试就失败。
  修法：按钮矩形内**多瞄点**退让（中心→左右→上下→四角内缩，每点各自过
  `elementFromPoint` 校验）+ 收浮层后**无条件重读**。
  注：此项仅有单测覆盖，真站未复现验证（该商品发布后编辑页不再渲染 SKC 行）。

## 八、类目误判连带尺码全错（2026-08-29 真站取证并修复）

商品 `1055568943470`（1688 标题「棕色女亚马逊牙雅跨境现货坑条短袖上衣夏季宝宝花朵
印花牛仔裤棉」，草稿 `173539495458370139`）在阶段⑧ 报「源尺码在页面选项里全部不
存在」。追下去是**两个独立 bug 叠在一起**，前一个把后一个盖住了。

### bug 1：③ 类目只看标题，把童装判成成人女装

逐级理由自相矛盾：第 1 级判出「女宝宝服装…符合婴儿服饰及鞋靴」，第 2 级却反转成
「女士时尚…并非女童或婴儿类目」，一路走到叶子「女士牛仔两件套」。触发点是 1688 标题
里「女」（指女款）与「宝宝」并列，「女」独立成词更容易被读成女士。

而同一份 `product-info.json` 里躺着三个比标题措辞硬得多的信号，此前一个都没喂给
类目判断：`attributes.适合年龄段`=`婴幼童(1~3岁，80~100cm)`、`sizes` 是月龄码、
`适合身高` 的厘米区间。

错类目下④ 属性照样填满 11/11、⑦ SKC 也正常（成人女装与童装属性行大量重合），
整条链上第一个对年龄段敏感的环节就是⑧ 的尺码交叉比对——错误延后约 5 分钟才暴露。

修法：
- 新增 `size_tier()`：按尺码写法判 `baby`/`adult`/判不出。月龄码（`6-9m`）、岁码
  （`2-3y`/`3T`）、身高码（`90`/`110cm`）与成人字母码（`S`/`M`/`Asian One-size`）
  是互斥的两套体系，这比标题措辞可靠。两档混杂或判不出一律返回 `""`，
  **绝不据此否定 LLM 的判断**。
- 新增 `cat_clues()`：把年龄段 + 尺码档位拼成一段线索，附在两条路径（遍历 +
  缓存快路径）的提示词里；规则 2 写明「线索里的年龄段/尺码写法优先于标题措辞」。
  线索为空时整段省掉，不留空占位（空占位会诱导模型自己编年龄段）。
- `auto_cat` 增加 `info=` 入参（service 从 `info_path` 读整份，CLI 加 `--info-json`）；
  不传则退化成原来的只看标题，判断逻辑一行不变。
- ⑧ 的报错在两侧档位相反时改口指认真因（「真因是类目选错，不是尺码别名」+ 当前
  类目路径），并把结论放在前 200 字符内——service 的 note 会截断，坠在尾巴上的
  结论人看不到。原文案前缀保留，2026-08-24 那道闸的测试仍然成立。

重跑取证：线索进提示词后第 2 级从「女士时尚」翻成「女童时尚」，每级理由都明确引用
线索，最终落在 `女婴裤套装`（母婴用品 > 服装和配饰 > 女婴服装和鞋靴 > …）。

### bug 2：`norm_size` 把月龄区间码截成单值，⑧ 多勾 8 个框还返回 ok

类目改对后⑧ 立刻暴露第二个 bug：`norm_size` 只取第一段数字，于是该类目 54 个选项里
的 `6M` / `6-9M` / `6-12M` / `6Y` / `6-7Y` **全部归一成 `6`**。源尺码 `6-9m` 把这
五个框全勾上——5 个源尺码勾出 13 个框、SKU 表从 5 行涨到 13 行。

而 `fix_sizes` 的收敛判据是「每个框的勾选态 == 归一值是否在 wanted 里」，在这种
碰撞下**恰好全部成立**，于是返回 `status=ok`（真站实测 `切换 8 次 | SKU 表 13 行`），
错误一路带到人工核对才可能被发现。

修法：月龄（`m`/`月`/`个月`）与岁（`y`/`t`/`岁`）分开、**区间两端都保留**——
`6-9m` / `6m` / `6y` / `2-3y` 互不相同。身高码分支放在月龄分支之后，行为不变
（页面身高码只有单值 90/100/110/120/130，没有这种区间碰撞）。
`3T` 按岁归一到 `3y`（美式学步童装同一档）。

修后真站复跑：`切换 0 次 | SKU 表 5 行`，页面勾选恰为
`6-9M / 9-12M / 12-18M / 18-24M / 2-3Y`。

### 顺带清理

错路径 `女士时尚 > 女装 > 女士牛仔 > 女士牛仔两件套` 当时已被 `remember_category`
记进 `workspace/publish-cache/categories.json`（回读校验通过，因为路径真实存在）。
已手工删除该条并备份为 `categories.json.bak-20260829`——否则下一个童装商品会命中
这条缓存，且缓存快路径没有任何下游校验能发现它是错的。

## 九、描述图尺寸闸门与⑧ 缺失尺码告警（2026-08-29 继续取证）

**同一单**（`1055568943470`、草稿 `173539495458370139`）续跑到 ⑬ 描述长图时又暴露
两个系统性缺口，都与上一节的两个 bug 无关：

### ⑬ 描述图尺寸闸门一律套服装 1340×1785，把达标的 480×480 拒掉

续跑到 ⑬ 时，第 10 张（计划 pos 12）复用已有英化产物 `d435b77317726ef0-en.jpg`
（480×480），被 `upload_image` 的尺寸闸拒两轮、页面上留着 1688 原始外链
（`cbu01.alicdn.com`），⑬ 最终以「1 张描述图不符合要求」整单失败——而那张图其实
是达标的（平台对描述图只要求两边 >= 480、比例 0.5~2，见 `images.check_desc_size`）。

根因：`upload_image` 的闸门下限硬编码 1340×1785（服装口径），不论用途。描述图、
素材图、SKC 图三条路径都调它，而只有素材/SKC 图才真的需要那道线；描述图本应按
`DESC_MIN_W/H`（480）过闸，却被服装下限拦住。

修法（`upload.py` + `pipeline.py`）：
- `upload_image` 增加 `min_w`/`min_h` 入参，按用途覆盖闸门下限（不传＝服装口径，
  行为一行不变）；闸门本身要留（它挡住了小图在图床静默弹回，排查成本远高于提前拒）。
- `desc_replace` 调用点显式传 `images.DESC_MIN_W`/`DESC_MIN_H`，按描述图下限过闸。

**上游根因：落盘产物尺寸不达标却仍当缓存命中。** 那张 480×480 其实是从源图 80×80
英化而来——`edit_image` 在 `desc_mode=True` 时对小图会自动放大到 480（就是这么
落盘的），但那只管画面内容（残留中文/乱码/主体改坏），管不到尺寸本身够不够。
`_prepare_desc_image` 的缓存命中分支原先只检查落盘文件是否存在、不复查尺寸，于是
历史产物可能是更早口径出的小图——就这样直接复用、交给替换去撞上传闸门。

修法（`service.py`）：缓存命中时对落盘产物尺寸复查一次，**读到了且低于下限**才
作废、当缓存未命中走放大分支；读不出尺寸（文件损坏/非图片）仍按命中处理，否则
会触发无谓的放大/重新生图（正是 `images.check_desc_size` 注释要避免的）。

### ⑧ 的 missing（源尺码在页面无对应框）被 service 层整个丢掉

续跑时 ③ 类目判断重跑并把人工改的「女婴裤套装」覆盖成「女童长裤套装」（这是我
判断续跑机制失误，本该先读懂 `_CAT_STAGES` 与 `_stale_form_stages` 的逻辑再动手，
而不是去改一个其实不会被读的状态文件字段），新类目的 56 个尺码选项里最小月龄档
从 `6-9M` 抬到 `9-12M`——源尺码 `6-9m` 在页面无框可勾，SKU 表从 5 行掉到 4 行。

⑧ 报的是「√ 源尺码 5 个 | SKU 表 4 行」——5 个源尺码只落 4 行，`missing` 警告被
`service._st_fix_sizes` 整个丢掉，note 里既没提缺失也没说是哪个，少了谁全靠人对
这两个数字。阶段正常 ok 照常走到 ⑭，缺的尺码只能人工核对时才发现。

**缺失往往意味着【类目选得不对】**（同一件商品换个类目尺码档位就全了），必须停下来
让人核对类目，而不是把它当成附注带过。

修法（`pipeline.py` + `service.py`）：
- `fix_sizes` 把 `missing` 单出一个键，不再只埋进 `warning` 字符串里。
- `_st_fix_sizes` 把它报成 `manual_check` 事件（进度里显式停一下），文案明确说出
  「源尺码 <哪个> 在本类目的尺码选项里不存在」+ 常见成因指向类目偏大/偏小。
  note 附上缺失的尺码值。

## 十、套装两张尺码表填出同一组数值（2026-08-29 真站取证并修复）

商品 <https://detail.1688.com/offer/1058585588864.html>（女童 T恤 + 牛仔背带裙两件套）。
截图现象：平台「尺码表」与「尺码表2」两个弹窗里，测量值**完全相同**——两张都是
衣长 45/48/51/54/47、胸围全围 54/56/58/60/57，只有尺码分类不同（一张女童装-上装、
一张女童装-连衣裙）。分类分对了、数值没分，等于给买家一份错尺码表。

### 源商品其实分件给了两张表

`desc-01.jpg`（尺码表信息图）上明确按部件分段：

- **(主) 部件：连衣裙** —— 前衣长 42/45/48/51/54、腰围 54/56/58/60/62
- **(主) 部件：上衣** —— 肩宽 21/22/23/24/25、袖长 9.5/10/10.5/11/11.5、
  前衣长 30/32/34/36/38、胸围 52/54/56/58/60

两件的测量部位本就不同（上衣量肩宽/袖长/胸围，裙子量裙长/腰围），而**同名参数
「前衣长」两件的数值也不一样**（上衣 30 起、连衣裙 42 起）——正是被混用的那一列。

### 两处成因（缺一不可）

1. **提取侧没有部件维度**：`extract._VISION_PROMPT` 只要求
   `sizeMeasurements = {尺码: {参数: 值}}` 一张扁平表，模型看到两张分件表时只能压成
   一份（本商品落库的就是「连衣裙的前衣长 + 上衣的肩宽/袖长/胸围」这种混合体）。
2. **消费侧两张表共用同一份**：`add_sizechart(which=0/1)` 两次都读
   `info["sizeMeasurements"]`。2026-08-27 那轮只修了**尺码分类**按件别分派
   （`_ACCESSORY_SIZE_CATEGORY`），取值仍同源——这个 bug 是同一个坑的另一半。

### 修法

- `extract.py`：`product-info.json` 新增 `sizeMeasurementsByPart`
  （`[{part, measurements}]`），提示词新增 3b 项，明确交代源图上
  「(主) 部件：X」的分段形态，并提醒别把「供应商尺寸/跳码规则/允差」当成尺码列
  （那几列就在同一张表里，很容易误读）。`_merge_vision` 单开一支收 list、丢掉缺
  `part` 或缺 `measurements` 的脏条目；**只有一件时不留**（一件等于没分件）。
- `pipeline.py`：新增 `_PART_SIZE_CATEGORY_KEYWORDS` / `_size_category_for_part`
  （部件名是商家手写自由文本，与包装清单词表不重合，故另建一张粗粒度映射）、
  `_category_keyword_of`（从平台选中的「女童装-连体衣」反推关键词，`category=None`
  跟随预选时用它配对）、`_pick_part_measurements`。
  **配对按尺码分类、不按序号**：源图部件序（连衣裙在前）与包装清单件序（上衣在前）
  不保证一致，本商品正好相反；配不上才退回按序号，那至少两张表数据不同。
  `_estimate_measurements` 加 `part` 参数——两件都要估算时不点明是哪一件，模型的输入
  完全相同（标题是整个套装的），必然给出同一套值。
- `service.py`：note 里报 `源部件 X`；两张表的 `data` 完全相同时发 `manual_check`
  （源只给合表时无从分开，故只告警不判失败）。

### 同轮补的两条套装护栏

**1. 同值告警只对混合套装（`skuCat=3`）。** 上面那条「两张表 `data` 相同就发
`manual_check`」一开始没区分 SKU分类，而 `skuCat=2` 是「多件相同商品」——两件同款、
尺码维度本就一样，同值是**正确结果**，在那里告警纯属误报。判据收紧到 `skuCat=3`。

**2. 包装清单三件以上要明确报出来。** 平台只有「尺码表」「尺码表2」两栏
（label 正则 `/^尺码表2?$/`，见 `_JS_SIZECHART_LOCATE`），`cats[1]` 硬取第二件，
`_pick_part_measurements` 的序号退路也只到 `which=1`，于是**第 3 件起静默丢弃**。
丢弃是平台结构决定的事实、改不了，但静默不行——人工复核时看不出「有 3 件、只进了
2 件」。现在补第二张表【之前】先发 `manual_check`，把件数与件别都列出来
（放在前面，人先看到有几件装不下，再看两张表填了什么）。

> 2026-08-29 当轮的实际商品是**两件套**，三件以上这条是按平台结构补的护栏，
> 尚无真站取证；真遇到三件套时应先核对平台是否仍只有两栏。

### 单测

- `tests/test_publish_sizechart_parts.py`（9 个用例）：部件名归类、按分类配对而非
  序号、配不上时两张表仍取不同份、`_merge_vision` 收/丢分件表、端到端两张表数值不同、
  估算提示词点明部件、以及**源只给扁平表时行为不变**（老路径不回归）。
- `tests/test_publish_sizechart_set_guard.py`（6 个用例，mock `add_sizechart` 不连
  浏览器）：混合套装同值告警、**同款多件同值不告警**、数值已分开时不告警且 note 报出
  两个源部件、三件以上报「平台装不下」且列出件别、两件套不报、单件不填第二张。

## 十一、数据采集页「未认领」清单（2026-08-30 新增，真站取证）

用户要的是**另一个列表**：发布页原有的「采集箱待编辑清单」扫的是【已认领】的草稿
（有店铺、有站点、有 rowid，只差编辑）；这次要加的是数据采集页
（`/web/productCrawl/dataAcquisition`）「未认领」标签下的采集记录——它们**还没认领**，
所以要走「认领 → 编辑 → 发布」的完整流程。

### 两个列表的差异（决定为什么必须是两个模块，不是加一个 state 分支）

| | 采集箱（`collectbox.py`） | 未认领（`crawlbox.py`） |
|---|---|---|
| 接口 | `POST /api/popTemuProduct/pageList.json` `dxmState=draft` | `POST /api/crawl/list.json` `state=no` |
| 主键 | 草稿 `rowid` | 采集记录 `idStr` |
| 店铺/站点 | 有（认领的产物） | **没有**——认领才产生 |
| 进度维度 | 编辑进度（逐个查 `edit.json` 判 6 个标记） | 可否认领（`operate.canClaim`，列表接口直接给） |
| 填任务框 | `源链接\|rowid`（跑① 提炼、**跳过**② 认领） | **纯源链接**（走完整 ①→⑮，② 真实认领） |
| 缓存文件 | `collectbox-scan.json` | `crawlbox-scan.json` |
| prefs 键 | `collectBoxScan` | `crawlBoxScan` |

合成一个模块会让「这一行有没有店铺站点」变成运行时才知道的事，而前端渲染与填任务框的
逻辑正是按这个分岔的（那边能自动带店铺站点、这边只能提示用户去选）。

### 四条真站取证（2026-08-30，都是「读错就静默出事」的）

**1. 主键必须取 `idStr`，绝不能取 `id`。** 实测一页 50 行的 `id` 与 `idStr`
**全部不相等**（如 `id=173539496022768700` / `idStr=...701`）。`id` 是 18 位雪花号
（1.7e17），远超 JS 双精度安全整数范围（2^53 ≈ 9.0e15），响应一进 `JSON.parse`
尾数就被抹平。本模块把它当去重键与前端行标识用，读错会让去重静默失真。

**2.「全部」标签不传 `state`。** 抓包实测点「全部」时 body 里连 `state` 与
`collectStatus` 两个键都不出现，不是传 `state=all`。故 `CRAWL_STATES["all"]["param"]`
是 `None`（表达「省略整个键」），取数 JS 据此拼 body。自造 `state=all` 的错在 UI 上
只表现为「计数对不上」，很难查。

**3. 计数不必另发请求。** `list.json` 的响应里 `data.stat` 直接给三个标签的计数
（实测 `{all: 1750, no: 397, claimed: 1353}`），故不像 collectbox 那样还要发一次
`count.json`——少一次请求少一个失败点。

**4. `canClaim` 不是「认领过没有」的判据。** 实测「已认领」标签的行 `canClaim`
**也是 true**——店小秘允许把同一条采集记录再认领到别的店铺/站点（`claim.py` 的
`_JS_TAB_CLAIMED` 就靠这条路处理「商品已被认领过」）。故它判的是「能不能发起认领」，
「认领过没有」只能由标签本身（`state=no/claimed`）决定。拿 `canClaim` 判会把 1353 条
已认领的行当成待认领，勾选后在 ② 凭空多建一堆草稿。

### 两个扫描器共用一把页面锁（`browser.PAGE_LOCK`）

`BrowserSession.open()` 是「挑一个店小秘页签复用」，于是两个各自 `new BrowserSession()`
的扫描器拿到的其实是**同一个页签**——各自在自己模块里加锁毫无用处，A 正在读列表时
B 一个 `navigate` 就把页面换走，且完全静默。故把锁提到 `browser.py`，
`collectbox._scan_lock` 也改成引用它。与发布作业的互斥仍走「作业跑着就跳过这一轮」
（拿锁拿几十分钟不现实）。

### 前端的三处刻意差异

1. **列不同**：没有「编辑状态/店铺/站点」，换成「可否认领/源价」。认领还没发生，
   那三样谈不上；而这批要先决定认领到哪个店，源价是选品时看的。
2. **源价两种币种都显示**：1688 是人民币、Temu 源本身是美元，只显示一个会让人误读
   一位数量级（0.59 元 vs 0.09 美元）。
3. **认不出平台的行直接剔掉而不是填进去**：采集箱的行认不出还能按 rowid 从某阶段续跑，
   这里连 rowid 都没有、没有任何续跑路径，填进去只会在 ① 炸掉。故标「不支持」（红字）
   并在填入时剔除、toast 里报跳过几行。
4. **店铺/站点不自动带、但每次都提醒**：本表给不出这两个值，而认领不可逆（选错店就
   认领到错的店铺，草稿只能手动删），故不管下拉当前选了什么都提示一句。

### 验证

- 单测 `tests/test_publish_crawlbox.py`（32 个用例）：与采集箱的三处隔离（缓存文件名/
  prefs 键/共用页面锁）、默认关闭、越界间隔与未知标签被拒、三个标签的 `state` 参数
  （含 `all` 传 `None`）、整行解析、不可认领的行列出但标出、`canClaim` 语义、
  翻页取满 limit 就停、扫描失败不覆盖上次清单、作业跑着时跳过、
  以及三条守取数 JS 字段口径的（只读 `idStr`、表单编码、`state` 为空时省略两个键）。
- 真站只读实测：三个标签各扫一次，条数/计数/平台分布/可认领数全部与页面一致；
  「全部」标签里确实混着 3 条 `canClaim=false` 的行（未认领标签里 0 条）。
- 页面实测（Playwright 驱动真实页面）：200 行渲染、摘要文案、全选跳过禁用行、

  无适配器的行被剔掉并报「跳过 1 行」、`operateHint` 有值时显示原文/无值时兜底说明。

## 十二、尺码表参数名对齐（2026-09-01 真站取证并修复）

### 现象

offer 999389808041（女童牛仔外套 + 连体裤两件套）填出的「尺码表2」里
**摆长 32/35/38/41/44**，而源详情图上的连体裤总衣长是 **59/64/69/74/79** ——差近一倍。
最初的怀疑方向是「视觉模型识图能力不够，2-3Y / 6-9M 这种月龄区间码读不出来」。

### 实际成因：识图无责，数据丢在填表前的参数名对齐

`product-info.json` 里 `sizeMeasurementsByPart` 的「连体裤」那份**完全正确**：
总衣长 59~79、腰围 48~56，源表里的「供应商尺寸」「跳码规则」这些干扰列一列都没混进来，
部件也正确拆成「外套」+「连体裤」两张。当时的全局模型是 `deepseek-v4-flash-vision-exp`，
它读这张表是满分。

丢数据的是 `add_sizechart._align_params`——原判据是纯子串包含（`k in p or p in k`）：

| 平台强制参数 | 源参数名 | 子串包含 |
|---|---|---|
| 测量全围 | 腰围 / 胸围 | 两个方向都不含，不成立 |
| 摆长 | 总衣长 | 两个方向都不含，不成立 |

对齐结果是空字典 → `need` 判为两列全缺 → 整份识准的源数据被丢弃 →
改交 `_estimate_measurements` 凭空估算。

**这条路一直靠巧合工作。** 同商品的第一张表（外套/上装）正常，纯粹因为
「前衣长」含「衣长」、「胸围」被「胸围全围」包含，子串刚好命中；此前只是没撞上
一组两边字面完全不搭的参数名。对齐失败的代价不是少填一列，而是**整列改用凭空估算的
值**——比缺值更糟，缺值会被 `lacking` 拦下报错，错值一路填进真店。

### 修复

**1. 三级对齐判据（`_match_param`）。** ① 字面/剥量法后缀（全围|半围|周长|围度）相同
→ ② `_PARAM_SYNONYMS` 词表按登记顺序取第一个命中 → ③ 子串包含兜底（原行为，
撤掉等于回退「胸围↔胸围全围」）。词表键用**裸词**，一个键覆盖「腰围」「腰围全围」两种写法。
`_PARAM_STEM_KEEP` 保住「测量全围」不被剥成「测量」（那不是身体部位）。

不该误配的组合要守住：「裤内长」是裆到脚口，与「侧裤长/裤长」（腰到脚口）差一个裆深
（约 20cm），词表里只认真正的内长量法，不让它们互顶。

**2. 词表兜不住时先问名称映射，再退估算（`_map_params_by_llm`）。** 源参数名是商家在图上
随手写的自由文本（腰围(橡筋)、裤长(不含吊带)、九分裤长…），穷举不完；而问名字只是一次
几百 token 的极短调用，比整表重新造数划算。只对「一行都没对上」的参数问——部分尺码缺值
是源表本身不全，问名字没用。best-effort 吞异常，失败照旧走估算。

**3. 估算提示词要喂源原始行（`_estimate_measurements(src_rows=...)`）。** `known` 是对齐
**之后**的表，未对齐上的列已经被剔掉了：模型连「源给了总衣长 59~79」这条唯一可靠的档位
锚点都看不到，于是把摆长估成 32~44。已对齐过的参数不重复列，剩下的正是量级与档差参照。

### 同轮修的三条连带（都由这个商品暴露）

**1. `estimated` 只有第一张表记。** `service._st_sizechart` 的 `r2` 分支漏了这个字段，
于是套装商品的状态文件通篇没有「模型估算」字样，看起来像两张表都用了源实测值——
第二张表两列全是估算、且量级失真近一倍这件事在状态文件与 UI 上完全不可见。

**2.「连体裤」是包装词表的空洞。** 平台词表里只有护胸背带裤/连体睡衣/连体泳衣，
`连体裤/连体衣/爬服/哈衣/连身衣/背带裙` 归一不到就掉到「长裤」→ 尺码分类取「下装」，
而源部件名判出的是「连体衣」，两边配不上、靠序号兜底才碰巧配对成功。
已在 `_PACKING_ALIAS` 统一归到「护胸背带裤」（词表里语义最近的连身项）。

**3. 分类下拉唯一选项时不该判 fail。** 999389808041 / 1039758347697 / 827598413718
三单的阶段⑨ 全部以 `option-not-found（keyword=连体衣, options=['女童装']）`告败、
整张尺码表没填。唯一选项意味着平台已按已选类目把分类定死，关键词对不上只说明我们按
件别猜的词与平台措辞不同，而不是选错了档。改为跟随该选项并返回 `source='only-option'`。
**此时 `category` 非空却未被采纳，配对分件表的键必须改用回读值**，否则会拿一个平台
并未选中的词去配对。

注：日志里 `衣长 999.0` 那条怪异告警是 `tests/test_publish_sizechart_measure.py` 的
构造值，不是真站缺陷，排查时别顺着它走。

### 验证

- 单测 `tests/test_publish_param_align.py`（6 个用例）：后缀归一与 `_PARAM_STEM_KEEP`、
  三级判据各自的优先级、子串兜底行为保留、「裤内长 ← 侧裤长」不误配、
  以及 999389808041 那两列的真站回归。
- 全量 `pytest -k publish` 通过。
- 端到端复现原故障场景：两张表的 `need` 均为空，摆长取到源实测 59~79
  （原先是估算的 32~44），测量全围取到腰围 48~56。

## 十三、尺码表是详情文字里的明文（2026-09-01 真站取证并修复）

### 现象

offer 971999094281（韩系牛仔外套）的 `sizeMeasurements` 落成空表，阶段⑨ 的四个参数
全靠模型凭空估算。但那份数据一直在手上——详情接口的响应体里就是三行明文：

```
S 衣长59 胸围118 袖长57 肩宽52
M 衣长60 胸围122 袖长58 肩宽53
L 衣长61 胸围128 袖长59 肩宽54
```

尺码表**不在图里**，所以识图那条路径压根没机会看到它。

### 成因：详情 HTML 只抠了 img，文字整段丢弃

`_JS_DETAIL`（页面内 fetch）与 `_fetch_desc_imgs_direct`（直连兜底）两条取数路径都只
`match` 图片 URL，剥下来的 HTML 文字整段扔掉。抽样 31 个 1688 商品，16 个
`sizeMeasurements` 为空，其中只有这 1 单是文字形态、其余确实是纯图详情——**少数但真实
存在，且文字比识图更可信**（商家白纸黑字写的，没有 OCR 这道误差）。

### 修复

**1. 取数侧把文字带回来。** `SourceProduct` 新增 `descText`（通用字段，四个平台共用；
目前只有 1688 落地实现，另三家仍只取图）。`_JS_DETAIL` 多回传 `html`，两条路径都过
`extract.desc_text_of` 剥文字——与 `_RE_DESC_IMG` 同一条约定：**两条路径必须得出同一份
内容，故剥法收在一个函数里，不各写一遍**。

`desc_text_of` 只做「剥标签 + 去排版残渣 + 压空白」，**不做任何尺码语义解析**——取数
必须是确定性的（同一个响应体永远得出同一份文字），解析是下一步的事。残渣清单来自真站
样本：`var offer_details={"content":`、`{"styleType":"offer-type-1","items":…}`
（关联推荐位配置）、`&nbsp;`/`&quot;`/`null`。尾行常是 `null"};`，判据用 `re.fullmatch`
只丢「整行都是符号与 null」的行，含真实文字的行不动。

**2. 编码判据不能只数替换符。** GB18030 把 UTF-8 的中文字节**静默**解成乱码汉字
（实测「衣长」→「琛ｉ暱」），既不抛异常也不产生 U+FFFD，只数替换符时这份乱码会与正解
并列、再按顺序被声明编码抢先选中。改成「先严格解、能过的才算候选，UTF-8 优先」：
UTF-8 编码结构很严，一段 GB18030 中文按它严格解基本必败；反过来虽能过，但 UTF-8 那份
也过了且排在更前。原先写死 `gb18030 + errors='ignore'` 是成立的——那时只抠 ASCII 的
图片 URL，中文解错不影响结果。

**3. 阶段①b `enrich_desc_text` 走文本 LLM。** 登记为 `stage="extract_text"`
（`vision=False`，所以能在发布页给它配快档模型）。不用正则：排版由商家随手写，这单是
「参数名+数值」紧贴成串（「衣长59」没有分隔符），别家可能是制表符、可能带建议身高混排；
正则要覆盖这些就得堆一串互相打补丁的分支，而输入极短（这单 68 字 / 672 token / 2 秒）。

**两道省钱闸，纯图商品一次调用都不发**：`descText` 为空直接 skipped；有文字但
`_RE_SIZE_HINT` 一个词都不命中也 skipped（多数纯文字详情写的是发货/洗涤/售后说明）。

**4. 文字优先于识图。** `overwrite` 默认 **True**（与 `enrich_vision` 相反）：文字是商家
实测值、识图有 OCR 误差，这与「源实测优于模型估算」一脉。但**抽到空表时绝不拿空去清掉
已有值**，写入后标 `sizeMeasurementsSource="descText"` 供人工分辨来源。要保住人工标注
传 `overwrite=False`（CLI `--keep-vision`）。

排在 `enrich_vision` **之后**跑（要覆盖它），但**不受 `with_images` 约束**——这条路径压根
不看图，纯图详情商品只是 `descText` 为空、直接 skipped。同样 best-effort 吞异常。

### 与 §十二 的关系

抽出的参数名（衣长/胸围/袖长/肩宽）下游能全部对上平台强制参数（胸围全围 ← 胸围、
摆长 ← 衣长），靠的正是 §十二 那层三级对齐。两轮改动是同一条链的上下游：
§十二 修「拿到了源数据却对不上参数名」，本节修「源数据压根没被取回来」。

### 验证

- 单测 `tests/test_publish_desc_text_size.py`（11 个用例）：真站文字/纯图两种响应体的
  剥法、四种编码组合（含声明与实际不符的两个方向）、脏条目过滤、两道省钱闸零调用、
  文字覆盖识图、`--keep-vision` 保住已有值、空结果不清值。
- 真站验证：目标商品三个尺码四个参数全部准确抽出；7 个纯图商品的 `desc_text_of`
  全部归零（一次调用都不会发）。
- CLI：`python publish_inspect.py enrich-desc-text <info.json>`，不连浏览器。

### 一处测试约定要跟着改

`test_publish_llm.py` 原有一条「每个 LLM 阶段 id 都必须在 `service.STAGES` 里」的约定，
理由是对不上会「设了覆盖但不生效」（UI 上看着配好了，调用点传的 stage 与登记表 key 不是
同一个字符串，静默回落默认）。`extract_text` 是**第一个例外**：它在 `extract` 阶段
【内部】跑，不是可续跑阶段，进 `STAGES` 会让续跑下拉多出一个 `_STAGE_FUNCS` 里没有实现
函数的假阶段。

处置是加 `_NON_PIPELINE_STAGES` 白名单**显式登记这个例外**，而不是放宽判据——放宽了
下次真写错一个阶段 id 时这条测试就拦不住了。同时补一条反向测试，确认白名单里的 id
仍然真能配模型（`set_stage_choice` 接受它），免得白名单变成「免检」。
